01 / MONOLITH VS MICROSERVICES

先说清楚：微服务到底是什么？

微服务不是某个框架，而是一种架构风格：把一个应用拆成一组小而自治的服务，每个服务围绕一块业务能力构建、独立开发、独立部署、独立扩缩容，服务之间通过网络（API 或消息）通信。它的对立面是单体（Monolith）——所有功能打成一个进程、一个包、一起部署。

spectrum · 拆分粒度从左到右递增
🧱

单体 Monolith

一个代码库 · 一个进程 · 一起部署
  • 优点：开发简单、调试直观、函数调用不丢包、事务一条 SQL 搞定
  • 痛点：改一行也要整体发布；一处崩溃全站陪葬；只能整体扩容
  • 适合：新项目、小团队、需求还在剧烈变化时
📦

模块化单体

一个进程 · 内部模块边界清晰
  • 做法：代码按业务域分模块，模块间只走定义好的接口
  • 价值：享受单体的简单，又为将来拆分铺好了路
  • 适合：绝大多数中小团队的最佳起点
🕸️

微服务

多个进程 · 独立部署 · 网络通信
  • 优点：团队各管各的服务，独立发布；按需扩容；故障可隔离
  • 代价：网络会断、数据会不一致、排查要跨服务追踪
  • 适合：业务边界清晰、多团队并行、规模真的大了
部署独立性 ↑  ·  团队自治 ↑  ·  运维复杂度 ↑↑
一句话记住它

微服务 = 用「运维复杂度」换「组织扩展性」。它解决的核心问题不是技术性能，而是几十上百人没法在同一个代码库里互不踩脚地并行开发、独立发布。

工程直觉

不要一上来就微服务。单体的问题你能感觉到（发布排队、改不动），微服务的问题你要踩过才懂（网络分区、数据不一致、调试地狱）。业界共识是「单体优先」：先把模块边界做清楚，等痛点真实出现、团队规模撑得起，再拆。

02 / SERVICE BOUNDARIES

怎么拆？按业务能力，不按技术分层

拆分是微服务最难也最重要的决策。原则只有一条：沿着业务边界切，让每个服务高内聚、低耦合。DDD 里的限界上下文是最常用的刀法：「商品」在交易域是价格库存，在物流域是重量体积——语义变了，就是边界。

case · 同一个电商系统的两种拆法

✓ 按业务能力垂直拆

  • 用户服务：注册、登录、个人资料
  • 商品服务：商品信息、类目、搜索
  • 订单服务：下单、订单状态机
  • 支付服务：收单、退款、对账
  • 每个服务独立演进：改支付逻辑不用动订单代码，各自有自己的数据库

✗ 按技术分层水平拆

  • Controller 服务：所有接口
  • Service 服务：所有业务逻辑
  • DAO 服务：所有数据库访问
  • 改任何一个需求都要同时改三个服务、一起发布——这叫分布式单体，只继承了缺点
最常见的翻车：拆得太细

两个服务如果总是一起改、一起发布，说明它们本该是一个服务——边界切在了业务的"肉"上而不是"缝"上。判断标准：一次典型需求，最好只改一个服务。拆错的代价极高（合并比拆分难得多），所以宁可先粗后细。

康威定律 Conway's Law

「系统架构会复制组织的沟通结构」。反过来用它：想要什么样的服务边界，就组什么样的团队——一个服务最好归属一个团队（亚马逊著名的"两个披萨团队"），跨团队共管一个服务是事故温床。

用户在 App 上点了一下「提交订单」，在微服务世界里会发生什么？这条链路上有微服务的几个核心角色：API 网关统一入口，服务发现找到对方，服务间同步调用，以及消息队列异步解耦。点击"下一步"走完整条链路👇

API 网关在干嘛

客户端只认识网关一个地址。网关负责路由（/orders → 订单服务）、认证鉴权、限流、协议转换——把这些横切关注点收口在一处，几十个服务就不用各写一遍，客户端也不用知道内部拆成了什么样。

关键观察

注意链路的后半段：扣库存、扣款是同步调用（下单成败取决于它们，必须等结果）；而发短信、给推荐系统喂数据走的是消息队列（晚几秒无所谓，订单服务发完事件就返回了）。"结果影响主流程吗"是选同步还是异步的第一判断——下一节展开。

04 / SYNC VS ASYNC

服务间通信：打电话，还是发消息？

服务之间隔着网络，通信方式只有两大类：同步调用——像打电话，发请求后原地等回复（REST、gRPC）；异步消息——像发消息，扔进消息队列就走，对方什么时候消费是对方的事。点击切换，看同一个场景两种写法👇

demo · 订单创建成功后，通知下游
同步调用的隐藏炸弹：级联失败

A 同步调 B，B 同步调 C —— C 一卡顿，B 的线程全被占住等待，接着 A 也被拖死，一个服务的故障沿着调用链向上蔓延，全链路雪崩。这就是为什么同步链路要尽量短、必须配超时和熔断（下一节）。

怎么选

问自己一个问题：「调用方需要这个结果才能继续吗？」需要（下单要知道扣款成败）→ 同步；不需要（发短信、记日志、刷缓存）→ 异步。异步的代价是最终一致性——下游晚几秒才知道，且消息可能重复投递，消费端要做幂等。

05 / RESILIENCE

拥抱失败：熔断器怎么救命

单体里函数调用从不"丢包"，微服务里网络故障是日常。容错三件套：超时（别无限等）、重试（只对读和幂等写，且要加指数退避）、熔断（连续失败就别再调了）。熔断器是个三状态开关，亲手玩一下👇

simulator · 订单服务 → 库存服务（熔断阈值：连续 3 次失败）
试试这条路径

① 先发几个请求（成功）→ ② 把库存服务拨到「故障」，连发 3 个失败请求，看熔断器跳闸到 OPEN → ③ 再发请求，发现根本没打到库存服务，是熔断器秒拒的（快速失败，保护双方）→ ④ 点「等待冷却」进入 HALF-OPEN → ⑤ 把服务拨回「正常」再发一个，试探成功，熔断器闭合，恢复正常。

为什么"直接拒绝"反而是好事

下游已经病了，继续把请求砸过去只会让它永远好不了，还把自己的线程全部耗在等待上。熔断的本质是：用一小段时间的快速失败，换下游喘息恢复的机会，同时调用方可以走降级逻辑（返回缓存、默认值、友好提示），而不是整条链路一起卡死。

06 / DATA & SAGA

最硬的骨头：没有跨服务的事务

微服务的铁律：每个服务独占自己的数据库（Database per Service），别的服务想要数据只能走 API——否则你改个表结构要通知全公司，等于没拆。但代价立刻出现：下单要「订单库写订单 + 库存库扣库存 + 支付库扣款」，三个库没法包在一个本地事务里。怎么办？业界主流答案是 Saga：把大事务拆成一串本地事务，失败时用「补偿操作」把已完成的步骤逆向冲正。两条路径都跑一遍👇

simulator · saga：创建订单 → 扣库存 → 扣款
注意：补偿 ≠ 回滚

数据库回滚是"假装没发生过"，补偿是用一笔新的逆向操作抵消（扣了库存就加回去，扣了款就退款）。中间态是真实存在过的——别的服务可能已经看到了"库存 -1"。所以 Saga 给的是最终一致性，业务设计要容忍短暂的中间状态。

配套模式速览

事件驱动：服务完成本地事务后发布事件（OrderCreated），下游订阅驱动下一步——上面模拟的就是这种"编舞式 Saga"；Outbox 模式：「写库」和「发消息」不是原子的，先把事件写进同库的 outbox 表（同一个本地事务），再由后台进程搬运到消息队列，保证两者不脱节；CQRS：跨服务的复杂查询，靠事件把数据冗余成一张专门的"读表"，别在线串调五个服务拼数据。

07 / OBSERVABILITY & DEPLOY

跑起来之后：看得见，才敢拆

一个请求穿过 8 个服务，哪一跳慢了、哪一跳挂了？单体时代 grep 一下日志就行，微服务必须靠可观测性三支柱。点击卡片逐个看👇

interactive · 三支柱，各答一类问题
部署底座：容器 + 编排

几十个服务 × 多个实例，靠人肉部署不现实。标准答案：每个服务打成容器镜像（Docker，环境一致、秒级启动），交给 Kubernetes 编排——它负责调度实例、故障自愈（挂了自动拉起）、滚动升级、按负载自动扩缩容，还内置了服务发现和负载均衡。CI/CD 流水线把"提交代码 → 测试 → 构建镜像 → 上线"全自动化，这是"独立部署"承诺真正兑现的地方。

微服务成熟度自查

敢说自己微服务玩明白了，至少要做到：① 任何服务可以随时独立发布（不用拉群约时间）；② 任何一跳故障不会雪崩（超时/熔断/降级齐全）；③ 任何请求可以一键追踪全链路；④ 新人半天能在本地把一个服务跑起来。做不到的话，痛点清单就是你的路线图。
